# TenderHack SPB — Полная картина

> Последнее обновление: 23.05.2026

---

## Суть задачи

Портал поставщиков zakupki.mos.ru хочет инструмент для закупщиков госучреждений. Закупщику по **44-ФЗ** нужно обосновать **НМЦК** (начальную максимальную цену контракта) — доказать, что цена рыночная. Сейчас это 2–4 часа ручного копирования с маркетплейсов. Нужно автоматизировать за 30 секунд.

---

## Что строим

**Интеллектуальный сервис поиска цен:**

1. Пользователь вводит запрос + регион
2. LLM расширяет запрос (синонимы, исправление опечаток)
3. Параллельный парсинг **4 источников**
4. Результаты появляются **постепенно** по мере нахождения
5. Итог: карточки товаров с фото / ценой / характеристиками / ссылкой

---

## Критические ограничения

> Нарушение = снятие баллов или дисквалификация

| Запрещено | Разрешено |
|-----------|-----------|
| Любые внешние API (OpenAI, Google, Яндекс Search, Bing и любые другие) | LangChain / LangGraph / n8n — **только если локально, без подписок** |
| Яндекс Спеллер API | `symspellpy` — локально, без интернета |
| Low-code / no-code платформы | Ollama + Qwen2.5 **7B** (не больше!) |
| Модели тяжелее 7B — жюри штрафует | Playwright, httpx |
| Фиксированный список сайтов для 4-го источника | Агентный подход (LangChain) — динамический выбор |

## Архитектура

### Ключевые решения

| Слой | Решение | Почему |
|------|---------|--------|
| Backend | FastAPI + `asyncio.as_completed` | НЕ `gather` — нужен стриминг по мере готовности |
| Стриминг | Server-Sent Events (SSE) | Каждый парсер шлёт данные сразу как нашёл |
| Frontend | `EventSource` API | Нативный браузерный SSE-клиент, карточки появляются динамически |
| LLM | Ollama + Qwen2.5:7b | Self-hosted, данные не покидают контур, лучшее качество на русском среди open-source |
| Spell-check | symspellpy локально | Яндекс Спеллер = внешний API = запрещён |
| Парсинг | Playwright (Ozon, ЯМ, Рунет) + WB публичное API | WB API открытый — без блокировок |
| Кэш | Redis TTL 30 мин | Если источник упал — показываем кэш, не падаем |
| Деплой | Docker Compose | Требование: Linux |

### Прогрессивная загрузка (ВАЖНО для UX)

Результаты появляются **НЕ все сразу** — по мере нахождения каждым источником:

```
~1-2 сек  → WB        (публичное API, самый быстрый)
~3-5 сек  → Ozon      (Playwright)
~5-8 сек  → ЯМаркет   (Playwright)
~8-15 сек → Рунет     (агент + Playwright, самый медленный)
```

```python
# Backend: стриминг вместо ожидания всех
async for source, products in stream_sources([wb, ozon, ym, runet]):
    yield ServerSentEvent(source=source, data=products)
```

```js
// Frontend: карточки появляются по мере прихода
const source = new EventSource('/search/stream?q=...')
source.onmessage = (e) => appendCards(JSON.parse(e.data))
```

### 4-й источник — агентный подход

- LangChain агент **динамически** выбирает сайт под конкретный запрос
- Playwright scraping DuckDuckGo Lite → топ-5 ссылок → открываем каждый → ищем цену regex `\d[\d\s]*₽`
- Дедупликация: если агент нашёл WB/Ozon — выбрасываем, они уже есть
- **DNS — пример как НЕ надо**: на их странице нет цен → агент должен уметь это определить

## Роль LLM — строго ограничена

```python
# ТОЛЬКО это — расширение запроса:
def expand_query(query: str) -> list[str]:
    # "шина летняя 205" → ["шина летняя 205", "летние шины R205", "автошина 205 лето"]
    pass

# LLM НЕ делает:
# - ранжирование результатов
# - сравнение товаров
# - объяснения
# - любые другие функции
```

`max_tokens=100` в промпте — чтобы Qwen не «фантазировал»

## Нюансы от заказчиков (транскрибация)

| Тема | Что сказали |
|------|------------|
| Подход к разработке | **«Идти с конца»**: сначала открыть страницу товара → понять где цена → потом строить поиск. НЕ наоборот. |
| Парсер | Хотят **абстрактный парсер** — не «парсер для Ozon», а «парсер любого сайта» |
| 4-й источник | «Задача со звёздочкой», хотят агентный подход. DNS — пример антипаттерна |
| LLM | Только переформулирует/расширяет запрос. Не ранжирует, не сравнивает |
| Синонимы | **Низкий приоритет** — «не стараемся много времени вкладывать» |
| BPMN | Технические компоненты (парсеры, LLM, кэш, DB) + swimlane пользователя. **НЕ** пользовательский путь |
| Vibe coding | Жюри будут спрашивать **каждого члена команды** про его код — все должны понимать свою часть |
| Отказоустойчивость | Если источник упал → показываем кэш, не падаем |
| LangChain/n8n | Разрешены если локально без подписок |

## Anti-blocking стратегия

| Источник | Метод |
|----------|-------|
| **WB** | Публичное API — без блокировок |
| **Ozon** | Playwright с задержками |
| **ЯМаркет** | Playwright + ротация User-Agent |
| **Рунет** | Playwright → DuckDuckGo Lite (Search API запрещены!) |

```python
async def fetch_with_retry(url, max_retries=3):
    for attempt in range(max_retries):
        await asyncio.sleep(random.uniform(0.5, 2.0))
        try:
            return await client.get(url, headers=random_ua())
        except RateLimitError:
            await asyncio.sleep(2 ** attempt)
```

## Вопросы жюри — готовые ответы

| Вопрос | Ответ |
|--------|-------|
| Почему Qwen2.5 7B, а не больше? | Жюри штрафует за тяжёлые модели. 7B достаточно для expand_query — задача простая, много токенов не нужно |
| Почему не внешний LLM API? | Заказчик требует зависимости только под своим контролем. Данные закупок не должны покидать контур |
| Как масштабировать? | Новый источник = новый класс BaseParser. Горизонтально — добавляем воркеры |
| Почему DuckDuckGo? | Все поисковые API запрещены. DuckDuckGo Lite парсится Playwright без API-ключей |
| Что если источник упал? | Redis кэш TTL 30 мин. Показываем кэшированные данные, не роняем весь поиск |
| Rate-limit обоснование? | `asyncio.sleep(random 0.5–2s)` между запросами + экспоненциальный backoff. Имитирует поведение человека |
